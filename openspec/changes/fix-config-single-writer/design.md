# 同一数据根的配置写锁设计

## 1. 先确认故障所在

历史记录确认两个桌面进程在同根运行时都报告「可写」。它没有记录锁文件身份或独占探测结果，因此双持锁、路径偏差、锁提前释放、状态展示失真均须用证据区分。先用现有构建和隔离数据根跑两个真实桌面进程。优先核对 PID、二进制路径、工具层徽标、两进程的绝对数据根及来源、锁文件设备号与 inode，再追踪句柄生命周期和独占申请结果。`ConfigStore::open` 的生产调用点只有启动与异常恢复，正常可写路径无运行期替换 store 的操作。展示与普通提交的锁门禁共用打开时取得的 `writable` 快照，无运行期 OS 复核。使用有效且会改变配置的命令核对实际提交，排除输入校验、空操作或写盘错误。首轮旧构建若无法重现，保留环境、命令和差异，根因继续标为未定位。

静态检查可直接确认三个需要覆盖的路径。

| 路径 | 当前源码的行为 |
|---|---|
| 启动与状态发布 | `ConfigStore::open` 以 `File::try_lock` 判定可写，存储进入 `PageHost`，设置面板读配置状态的 `writable`。现有双进程测试走存储模块测试进程，桌面启动与状态发布未在这条测试中运行。 |
| 显式重取 | `ConfigStore::try_acquire` 先置 `writable = true` 再 `reload`，重读错误时缺少回退。该方法目前未接到桌面命令。 |
| 备份重建 | `rebuild_with_backup` 在独占锁内写入，函数返回后释放锁，`config_rebuild` 随后再调用 `ConfigStore::open`。两步间有竞争窗口。 |

出处见 [配置存储](../../../apps/desktop/src-tauri/src/config_store.rs)、[桌面编排](../../../apps/desktop/src-tauri/src/lib.rs)和[归档实机结果](../archive/2026-11-18-add-project-device-profiles/evidence-index.md)。

## 2. 持锁与写入使用同一状态

复用根内固定的 OS 独占文件锁，保留文件句柄作为实际持有凭证。先核实各入口打开的是同一实际文件，包括同一根经绝对路径别名访问的情况。应用留存 `projects.lock` 并复用它，避免移除或替换文件后同时锁住两个不同文件。两个不同实际数据根各自独立。已存在的空锁文件仍须以 OS 申请结果判定占用，避免把正常残留当永久锁。维持平台释放语义，正常退出等待已开始的事务，异常退出后由 OS 收回句柄。

锁争用和配置内容有效性分别表达。启动读取到损坏配置或未知版本时报告内容错误，保持常规写入关闭，无可用 store，释放本次启动取得的锁；即使已有其他实例持锁，启动也应读盘并报告内容错误。有效的只读快照与无有效配置的状态分别展示。`PageHost` 当前通过 `OnceLock<ConfigStore>` 共享存储，只提供 `&ConfigStore`。重取从共享引用进入；锁句柄、配置快照、revision 和写入资格在存储内部的同一互斥状态中裁决。取得锁后先读盘验证，再连同新快照一起发布；失败释放候选句柄，保留加载错误和禁写状态。锁 I/O 错误沿用 `CONFIG_READ_FAILED`，真实争用沿用 `CONFIG_LOCKED`。独占锁与可写状态的判定覆盖实际提交所用的临界区，保留现有的 revision 检查、同目录临时文件及原子替换。避免在共享配置状态锁内等待网络、页面事件或 UI。

逐一检查创建、编辑、视口、跨项目切换、最近地址自动记忆、未保存重试、重建和退出。普通配置修改入口先判定写入资格，再处理输入、布局或页面切换；提交时仍核验持锁状态和 revision。将 `config_retry_unsaved` 当前只读分支的 `CONFIG_WRITE_FAILED` 改为 `CONFIG_LOCKED`，优先于有无待保存意图的判定。备份重建在复查和备份前通过同一锁仲裁。可写实例重新选择当前项目的现有无重载行为继续适用。

## 3. 只读、显式重取与页面归属

- 设置面板单独显示「配置只读」和「重取配置写锁」入口。数据根是否可写继续表示目录本身的检测结果。命令的成功、仍被占用和读取错误经底部独立状态栏显示，后端统一保护直接命令调用。启动保留 `startup_restore` 的项目与视口恢复，使用已读的有效只读快照。只读期间发起的恢复导航、项目归属导航、重定向与临时浏览只更新页面。`remember_last_loaded_url` 在提交前核对导航发起时的写入资格与回调时的锁状态。任一不满足就跳过记忆与失败恢复路径，不创建 `UnsavedState` 或显示「未保存 / 可重试」红条。持锁发起的有效项目导航仍沿用现有写盘失败处理。
- 用户触发重取时尝试一次非阻塞申请。仍被占用时保留只读与已有只读快照。申请成功后从磁盘验证完整配置；读取、解析或版本失败时释放本次锁，保持常规写入关闭，并显示相应错误。成功时先用最新快照刷新项目列表、活动项目和 revision，再允许新操作，旧草稿与重取前已排队的配置意图失效。过期 revision 继续返回 `CONFIG_STALE`。
- 重取配置锁本身不导航或恢复页面。已有页面可继续显示，重取前发起的只读导航及其回调继续按发起时的资格判定。后续明确进入已读项目时沿用页面身份校验，避免旧地址写入交接后的活动项目。并发重复重取、重取与退出按同一状态机串行裁决。

## 4. 损坏配置和备份重建

损坏或版本未知的启动实例没有持锁 store。两个这类实例均可在用户确认后请求重建，由 `projects.lock` 仲裁，仍被占用的实例以 `CONFIG_LOCKED` 拒绝。显式重取后报告配置损坏或未知版本时，同样可进入确认重建，入口按恢复状态裁决，不能仅检查 store 是否已初始化。持有健康快照的只读实例仍须完成显式重取才能发起配置修改。取得锁后复查磁盘状态。磁盘若已是有效配置，则返回既有「无需重建」结果并保留数据。读取错误或备份失败保留原文件，重建成功才交付新配置。重建从复查原始字节、完整备份、原子替换到新状态发布连续持锁。重建内部复用恢复入口刚取得的同一持锁句柄，并将其交给已就绪的存储。持有期间禁止打开同一文件的第二个句柄再次申请。保留原有十份备份上限、显式确认和旧截图保护。

## 5. 验证层次

保留存储级子进程检验，再增加覆盖生产状态转换和命令门禁的机器用例。用同步点控制重读、重建交接、退出及迟到意图顺序。既有 `cargo test --lib` 与公共门禁承担可重复断言。真实桌面进程负责证明启动路径、实际 OS 锁及窗口反馈，按[证据索引](evidence-index.md)记录。复验只使用隔离数据根与可控页面，生成内容留在 `.layress/` 或 `artifacts/`，仓库只留方法与结果。
