# i18n · 双语口径

> 本文默认以中文维护。

本目录管两件事：**文档层双语**（现在生效）与**产品字符串层双语**（`packages/` 有代码后生效）。
口径来源：国际化 = 中国用户优先 + 英文产品名 + 具备海外发布能力，不是"把产品改成英文"。

## 范围与两层结构

| 层 | 内容 | 状态 | 强制方式 |
|---|---|---|---|
| 文档层 | 默认中文；逐篇登记的对外文件维护同目录 `*.en.md` | 生效 | `node scripts/check-i18n.mjs` |
| 产品字符串层 | Web 工作台、CLI 人类可读输出、错误文案的 `zh-CN` / `en-US` 资源 | 未启用 | 同脚本扩展 + 批次归属清单 |

字符串层落地时的形态（写在这里是为了现在别把目录设计成不支持它）：
`packages/i18n/locales/{zh-CN,en-US}/*.json` 同键结构、带插值参数与富文本槽位，
默认 `zh-CN`，英文入口不做机器翻译。

## 成对规则（文档层）

- **文档默认中文**。当前维护中英双版本的对外文件仅为根目录 `README.md`、`CONTRIBUTING.md`、
  `SECURITY.md`、`CODE_OF_CONDUCT.md`、`CHANGELOG.md`。
- `AGENTS.md`、`docs/` 全部文档（含指南、架构、工作流、经验库、方案、调研）、`i18n/` 维护说明、
  数据集与 OpenSpec 文档无需翻译。仓库公开可见不等于每篇文档都有中英双语维护义务。
- 以后某篇文档确有对外阅读需求，再逐篇提供英文并加入 [`docs-manifest.json`](docs-manifest.json) 的 `docs`；
  不按目录整批翻译。中文是源，英文用同目录 `X.en.md`，不建 `en/` 子目录，登记后两份同轮修改。
- 已有内部英文版移入 `docs/drafts/YYYY-MM-DD-internal-translations/` **本地归档**，附原路径索引；
  该目录已忽略且洁净度门禁禁止入库。中文页移除旧语言入口，当前规则以中文为准；历史原文也可从 Git 查找。
- 只写中文且未登记无需配对；登记为对外文件却缺译本仍判红。当前目录中的新 `*.en.md` 未登记时，
  以 `TWIN_UNREGISTERED` 判红；已忽略的本地归档不参与检查。

## 表单与模板：不做两份

Issue 表单和 PR 模板翻成两份会让提交者不知道该填哪个，也让人没法比对两份是否同口径。做法是：

- **GitHub Issue 表单**（`.github/ISSUE_TEMPLATE/*.yml`）：同一表单内并列 ——
  `name: Bug report / Bug 报告`、`label: What happened / 遇到的问题`，
  说明块里英文段落在前、中文段落在后。一份表单，两种语言都能填。
- **PR 模板**（`.github/PULL_REQUEST_TEMPLATE.md`）：小标题用 `## Summary / 改动说明`，
  填写指引以 `<!-- 英文 -->` 紧跟 `<!-- 中文 -->` 成对给出。
- **Gitee 侧**（`.gitee/*.zh-CN.md`）：纯中文。面向大陆网络环境的贡献者不需要再看英文。
- 三个位置的口径必须等价：改任一处，另外两处同轮跟上（人工核对，脚本不查 yml 与 md 的语义等价）。

## 语言入口格式

每份成对文档在一级标题**下一行**给出互链，中文指向英文、英文指回中文：

```markdown
<p><a href="README.en.md">English</a> | 简体中文</p>
```

英文页写为 `<p><a href="README.md">简体中文</a> | English</p>`；链接标签必须是目标语言，标反即 `LANG_LABEL` 判红。缺入口即 `NO_LANG_LINK` 判红，目标路径必须解析到实际配对文件。入口放在标题紧邻处；脚本不检查排版位置。

## 翻译纪律

- **同轮改动（仅登记的对外文件）**：口径变更必须中文与英文一次提交内完成。内部文档只维护中文；分两次提交会让对外英文停在旧口径，
  而读者以为它说的是当前事实——比没有英文版更糟。
- **对齐结论，不对齐句子**：中文句子该拆就拆、该合并就合并，但段落顺序、小节数量、表格行数、
  结论与警告必须一致。门禁按 `##` 小节数与代码块数比对，漂移即判红。
- **原值不翻译**：代码标识、协议字段、错误码、文件名、CLI 参数、CSS 属性、单位、包名一律保留原样。
  术语对应关系查 [`glossary.md`](glossary.md)。
- **数字与判据不许顺手改**：门槛、计数、日期在两份里必须字面一致；改一处忘一处是典型的口径分叉源。
- 英文版本由人写，不机器直出：术语表冻结后才开始批量翻译，否则同一概念三种译法。

## 门禁

```bash
node scripts/check-repo.mjs --all        # 本地与 CI 的公共门禁入口
node scripts/check-i18n.mjs --links      # 全部已跟踪 Markdown 的本地链接，与双语范围无关
node scripts/check-i18n.mjs              # 仅登记表内的成对文档
node scripts/check-i18n.mjs --selftest    # 反证：缺对/断链/漂移/语言标签必须判红
```

检查项：`TWIN_MISSING`（缺英文）· `ZH_MISSING`（登记了但原文不存在）· `NO_LANG_LINK`（语言入口）·
`NO_TITLE` · `LANG_LABEL`（语言标签标反）· `HEADING_DRIFT`（小节数漂移）· `CODE_BLOCK_DRIFT` · `THIN_TWIN`（英文体量异常）·
`BROKEN_LINK`（本地目标路径不存在）· `INVALID_LINK`（路径编码无效）· `TWIN_UNREGISTERED`（孤儿英文）。

`--links` 独立检查全部已跟踪 Markdown 的文件目标，包括内部中文文档、仓库根路径、Markdown 引用式链接与 HTML 链接；不联网验证外链，也不检查标题锚点。代码示例与本地归档不参与检查。

`--selftest` 是门禁的自证：10 个反例 + 1 个正例，覆盖语言标签、内部中文断链、根路径与引用式链接，正例同时覆盖内部中文免配对、编码路径和本地归档排除。临时夹具只写入 `artifacts/` 并自动清理。没有它，一条永不命中的规则会长期表现为"双语全绿"，
而实际上一条都没检查。Workspace 落地后并入 `pnpm check:i18n`，进 `check:ci` 链与 CI。
