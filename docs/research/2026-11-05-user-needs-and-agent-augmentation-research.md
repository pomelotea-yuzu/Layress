## 一、本轮调整：以已经拥有强 Agent 的用户为起点

用户提出了两个需要同时满足的目标：**人愿意主动打开 Layress；不同 AI Agent 能方便地调用 Layress，获得能力增强**。因此，调研不能只找现有工具没解决的特殊缺陷，也不能只证明过去有人被截图、脚本或登录问题困扰。

基础功能决定一次检查能否方便地完成；差异化能力决定额外使用 Layress 是否值得。能力已有替代品，不等于需求不重要；需求确实存在，也不等于必须自研或需要一个独立应用。

后续比较的起点应是：用户已经可以请当前 Agent 阅读代码、编写 Playwright 脚本、操作浏览器、查看截图并整理结果。具体 Agent 在这些任务上的效果仍需实测，不能预设它一定失败，也不能因为模型能力强就预设这些任务均已可靠完成。

本轮采用的工作假设是：Layress 若有价值，应帮助人和 Agent 更省事地完成界面检查，提供可控制的执行与可核对的证据；**“增强 Agent”是新的评价视角，尚不是已证实的产品优势**。

| 当前证据缺口 | 没有当前 Agent 同任务对照、目标用户实际试用、完整访谈或付费验证 | 已有用户本人这一调查起点，尚不能确定更广用户群、功能排序、持续使用频率及独立应用形态是否成立 |

## 三、先覆盖一次完整的基础任务

初步任务链：**进入实际待测页面 → 选择目标尺寸和状态 → 查看页面与常用操作 → 留下能交接的证据 → 修复后重复检查**。

下表是待验证的最低完成标准，不是首版已批准功能表。尺寸、语言、页面和操作由实际用户任务决定，不用预设全量设备矩阵代替需求判断。

| 基础任务 | 人使用应用时期待什么 | Agent 调用时需要什么 | 尚须验证 |
|---|---|---|---|
| 快速开始 | 待测对象、准备步骤与检查范围清楚，不为简单任务额外强制注册工具账号 | 可发现能力和环境要求，输入可明确传入，缺参能够解释并退出 | 相比已有浏览器、脚本或 Agent 工具，新增接入步骤是否值得 |
| 检查常用尺寸与条件 | 方便切换少量自选宽高，知道实际生效的尺寸、缩放和语言，必要时留图 | 条件可配置、读回并记录，能对同一状态重复检查 | 先后切换、并排预览和批量检查各自适合哪些任务，不默认同时多视图必需 |
| 到达真实业务状态 | 能进入登录后页面、目标弹窗或菜单，明确哪里仍需人工准备 | 能衔接已有登录状态、脚本或准备步骤，知道状态是否有效 | 认证复用、状态过期、共享账号与外部副作用的实际成本；不承诺任意应用自动探索 |
| 理解并交接结果 | 现场与条件对应，看得出问题位置、操作影响及待确认项，输出容易找到 | 有版本的结构化结果、证据引用和清晰的执行 / 判定状态 | 截图、现有 trace 或报告附件是否已经足够，哪些信息还需要额外提供 |
| 修复后低成本重查 | 找回上次上下文，重新核查相同任务，区分未执行与通过 | 结果能衔接下一次调用，准备条件和重复执行的限制明确 | 环境漂移、配置维护与误报处理是否抵消节省的时间 |
| 在已有流程中采用 | 不必整体迁移测试与审核方式，可以先完成一件具体任务 | 不依赖特定聊天宿主或必须点击的 UI，已有脚本和工具可以接续 | CLI、MCP、Skill 各自的实际接入范围和代价；不能把列出协议等同于已兼容 |

基础截图、条件切换与结果交接即使不独特，也可能影响用户是否继续使用。裁切、溢出和遮挡等检查仍需区分几何候选、实际操作受阻与业务结果，不能用告警数量替代任务完成质量。

## 五、已有工具是基础设施，也是必须面对的替代方案

以下资料已在前轮读取正文，本文未新增工具实跑；具体能力与接入成本仍以实际版本和环境为准。

| 资料 | 已有能力 | 本文的使用方式 |
|---|---|---|
| [Responsively](https://responsively.app/) | 声明多视口、设备组合、操作同步、截图及检查器 | 作为人工多尺寸检查的现成替代，不预设必须重做同一套界面 |
| [Playwright Emulation](https://playwright.dev/docs/emulation) | 视口、设备预设、DPR、触摸、语言、时区和主题配置 | 优先研究怎样复用，而不是把参数配置本身当作优势 |

| [Playwright Reporters](https://playwright.dev/docs/test-reporters) | HTML、附件与结构化报告等输出 | 研究证据能否沿已有报告交付，不自动新建一套报告器 |

| [Playwright Best Practices](https://playwright.dev/docs/best-practices) | 可见行为检查、隔离、数据控制、定位与 trace 排障建议 | 为比较准备和排障成本提供参照，不冒充用户采用统计 |

## 六、两个入口共同成立的条件

应用与 Agent 接口共用核心事实、判定和证据。用户打开应用不应成为 Agent 完成检查的前置条件；Agent 入口也不能让人工复核者失去理解结果、控制范围或接续检查的办法。

| 入口 | 值得验证的价值假设 | 怎样才算有额外价值 | 可能推翻它的结果 |
|---|---|---|---|
| 人主动打开应用 | 查看现场、选择检查范围、比较状态和证据、复核结果，比在多个窗口和记录之间来回切换省事 | 同一真实任务中，更快找到相关证据、完成判断或发起重查，准备和学习成本未抵消收益 | 现有浏览器、Agent 对话或报告已经足够，独立应用只是增加一次切换 |
| Agent 调用能力 | 将环境控制、重复执行、证据采集与结果交接交给稳定的工具，减少临时编写和维护脚本的劳动 | 相同任务和预算下，减少用户介入、准备 / 排障时间或结果歧义，证据可供后续调用继续使用 | Agent 直接用浏览器或已有工具即可同样可靠、低成本完成，新增调用层没有净收益 |

这些是待证实的假设，不能提前声称“Agent 无法完成”或“我们的检测更准确”。Layress 不因采用这一评价视角就必须内置一个模型、聊天界面或自建 Agent 宿主。

既有路线图仍以 CLI 预览为阶段目标，桌面 UI 的实现时点未定。**用户愿意打开应用是本轮新增的产品评价要求，需要进入后续调研；是否据此调整交付顺序，要由证据决定，不能把尚未安排 UI 实现误写为不再评估应用价值。**

## 七、怎样把“任何 Agent 友好”变成可验证的约定

本项目已有 [I14 与 Agent 接口约定](../../openspec/config.yaml)，尚未实现。本文将用户的跨 Agent 要求理解为避免绑定单一宿主、模型和专用对话格式；真正支持到哪个客户端、版本和调用方式，必须逐项公布已验证范围，不能保证未经测试的所有 Agent 自动可用。

| 约定 | Agent 应能获得什么 | 后续验证要点 |
|---|---|---|
| 发现与输入 | 能力说明、输入输出 schema、环境限制；显式指定对象、操作、准备状态、条件、预算与数据目录 | 无 TTY 可调用，缺参不悬挂，不依赖 Agent 猜命令或必须点击 UI |
| 可解析的结果 | 有 schema 版本的结构化输出，日志与机器结果分开，稳定的状态和错误码 | 调用是否成功与缺陷结论分开；工具失败、超时、未执行和不确定不能变成通过 |
| 可核对的执行 | 实际条件、运行标识、证据引用、已完成范围与限制 | “执行可重复”与“模型判断必然一致”分别验证，不把截图描述直接当成事实或业务成功 |
| 后续衔接 | 下一步确认、缩减或回放可以引用已有结果与准备条件 | 附件可访问，路径语义明确；回放与会产生新副作用的重跑分开 |
| 用户控制 | 超时、取消、成本与副作用边界清楚，部分结果可保留 | 取消释放本次资源；外部提交、安装、账号操作或模型费用不因 Agent 调用而自动获准 |
| 通用接入 | CLI 作为可非交互调用的入口，MCP / Skill 按实际需要复用同一核心 | 测试不同宿主的输入传递、输出解析和错误处理；仅提供协议名不算兼容，交付时点另定 |

本轮本地核查还找到一个已登记的跨客户端边界：某些实际客户端没有把完整 `structuredContent` 交给模型，文本投影虽保留部分事实，外层游标和限制仍可能无法被直接消费。因此，“任何 Agent 友好”还应核查模型实际收到的状态、证据范围、截断提示与后续入口；不能只验证服务端工具发现和 JSON 形状。此处来自本地既有指南 / 历史证据与当前投影实现的核对，未重跑客户端，不定性为新缺陷，项目身份与具体证据指针仅保留在本地记录中。

本地优先、便携存储、机器 PASS 不等于人工验收，以及候选不等于缺陷等约束继续适用。若使用远程模型或把界面资料交给调用方的远程 Agent，必须说明实际数据流和成本；工具本地运行并不自动意味着完整 Agent 工作流的数据始终留在本机。

## 八、下一轮应怎样调研和比较

### 8.1 补当前 Agent 环境下的直接证据

用户本人就是此类应用的开发者，并已授权只读查看自有项目与本地候选清单。优先从其最近的开发和界面检查记录提取第一手任务，再按需要补其他用户；具体项目标识、绝对路径与私有证据继续只留本地草稿，不复制入库或上传外部服务。

需要调查的仍是最近一次检查任务：使用什么 Agent、模型版本和浏览器 / 测试工具，实际交付了什么，哪些步骤由人准备、核验或重复处理。已有项目文档和源码可以证明工作流与接口的存在，但不能独自证明运行效果、最新模型能力或省下的时间；接受“已有工具足够、不需要额外应用”作为有效结果。

本轮已完成本地资料的有限只读核查，得到以下任务入口；这是开发记录与源码事实的归纳，不是本轮运行结果，也不是已经选定的实验范围。

| 任务入口 | 已有材料说明什么 | 当前仍缺什么 |
|---|---|---|
| 语言切换后继续编辑，取消时保留草稿 | 近期记录覆盖草稿保持、旧确认撤销、取消后的焦点返回，并记录了保存期间禁用控件造成焦点丢失及其修复；当前局部实现有恢复逻辑 | 本轮未重跑；历史键盘证据为浏览器层受信事件，不等于 OS 物理键盘；准备、重复执行、找证据和人工复核耗时未知 |
| 调整窗口与缩放后阅读多栏和长内容 | 既有脚本和记录包含实测内容区、滚动、编辑器尺寸、按钮范围与多语言；部分有限正文空间由用户因必要诊断信息接受 | 不能把正文小、滚动或折叠直接认作缺陷；短名称夹具不能冒充长路径覆盖，应用缩放不能冒充完整系统缩放矩阵 |
| 编辑目标往返与结果定位 | 历史记录采用编辑器自身 API 检查滚动 / 光标 / 草稿恢复，已有后台完成与结果入口记录 | 本轮未验证当前行为；DOM 的通用滚动读数不总能代表复杂编辑器状态；尚无足够工时和介入记录 |
| 卡片筛选后查看详情、长题干下答题与下一题 | 自有应用中存在互补的浏览、弹层及连续表单操作入口，可用于避免只研究专业工具界面 | 独立合成数据、离线注入、存储隔离与启动条件尚未准备；不能直接使用用户媒体、题库或现有业务记录 |

**建议先整理第一个任务的现有准备步骤与判据**，研究一次普通改版后怎样重复完成它，再考虑卡片与表单任务。已有被修复的场景和正常状态同样有价值，不必先寻找尚未解决的特殊缺陷；现有 Agent 已有脚本、测量和证据组织基础，应比较新增能力是否减少重复劳动。

本地候选也不都属于 Electron：已有 Tauri、原生桌面 GUI 和 Canvas 等不同技术形态，不能把拥有 Web 前端或桌面窗口自动当成可共用 Chromium / Electron 接入。类型核查不等于可启动性与自动化兼容验证，不据此扩张首版平台。

仍需核实具体执行任务时的 Agent / 模型 / 工具版本，并按需要补近期官方能力和外部使用记录；这些取证不再作为开始研究用户本人任务的前置条件。访谈、发帖或对外联系另行授权，启动应用或有副作用的实验也须先确定具体范围。

### 8.2 用相同任务比较，而不是用特殊案例证明必要性

| 路线 | 比较什么 | 要防止的不公平条件 |
|---|---|---|
| 人工 + 已有浏览器 / 多视口工具 | 最简单的准备、检查、交接与修复后重查流程 | 不故意加入人工无需完成的复杂要求，以此夸大自动化收益 |
| 当前 Agent + 其已有浏览器 / 测试工具 | Agent 能直接做多少，哪些准备与核验仍需用户承担 | 不限制其正常可用工具，不用旧版或弱配置代表当前能力 |
| 同一 Agent + Layress 的有限能力 | 是否减少准备、执行、排障、复核或维护负担 | Layress 尚未实现；只有以后确定有限实验范围后才执行，不将此列为已跑对照 |

每条路线使用同一任务说明、页面状态、环境、权限、允许滚动方式与完成标准；记录 Agent / 模型 / 工具版本、预算和人工帮助。历史 VS Code 案例可作条件允许时的测试线索，不能成为唯一任务，也不能冒充普通用户的日常需求分布。

### 8.3 记录任务收益和人机交接

| 记录项 | 要回答的问题 |
|---|---|
| 到首次有效结果的时间 | 配置、登录与数据准备是否吃掉节省的时间 |
| 人的介入次数与耗时 | Agent 需要多少补充、纠正、现场检查与重新执行 |
| 结果可核查程度 | 能否把结论对应到具体条件、操作、现场与未执行项 |
| 重查与维护成本 | 修改代码或下一次会话后，能否重复相同检查，哪些配置需要重做 |
| 可靠性和误判 | 已知正常与失败状态能否区分，环境问题是否被错误归为通过 |
| 资源与费用 | 执行耗时、模型调用、临时脚本维护、存储与其他成本是什么 |
| 应用入口的净收益 | 主动打开应用完成了什么，是否比现有报告或 Agent 对话少一次来回 |
| 跨 Agent 接入 | 哪些独立宿主经过实际验证，差异在哪里，新增适配成本是多少 |

先记录原始步骤、数量和耗时；样本不足时不报代表性的成功率，也不把未执行的人工复核勾成完成。

## 九、继续、调整或停止的依据

- 基础任务有重复需要，且应用或 Agent 调用显著降低完整流程成本：继续研究最小可用范围，不要求每个基础功能独有。
- 主要收益来自 Agent 调用，人工独立打开的价值仍弱：保留增强能力的价值判断，同时继续核查应用入口，不据此宣称两个目标都已成立。
- 主要收益来自查看与复核，工具执行可直接复用：研究集成已有能力，避免为包装报告重复构建探针与执行器。
- 当前 Agent 或既有工具已以相近成本可靠完成：记录为反证，考虑插件、上游贡献、缩小范围或停止独立实现。
- 有收益但大量依赖临时脚本、手工准备或逐宿主修补：将维护成本计入，不能靠演示成功替代持续使用验证。

本轮完成的是既有证据整合、自有应用的有限只读核查与调研问题更新；具体项目、路径和证据指针仅保留于本地私有记录。**本轮当前 Agent 对照、竞品实跑、完整用户访谈、应用交互验证、跨 Agent 兼容复测、原始候选复现和付费验证均未执行；未启动或修改被查项目，未创建技术 change，未批准原首验方案，未启动 Layress 产品实现。**
