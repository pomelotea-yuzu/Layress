## 一、本轮结论与证据边界

- 已核查 7 条中英文社区讨论的问题、回答或评论，另核查 1 条真实缺陷记录及 4 份官方资料。它们支持继续研究复核成本、状态和环境控制，但不足以确定首批用户、发生频率或独立工具价值。

## 二、检索与核查方法

围绕“现有检查流程、误报与维护成本、已有方案足够的反证、真实操作受阻”检索，中文重点查看测试之家与 V2EX，英文查看 Stack Overflow、Hacker News 与 Reddit。检索词包括 `视觉 回归 测试 误报`、`视觉 基线 维护`、`testing responsive layout`、`screenshot comparison`、`playwright baseline screenshots update`。

搜索摘要仅用于找线索。中文讨论通过正文及评论核查；Stack Overflow 页面直接访问返回 403，改用官方公开 Stack Exchange API，读取问题正文、创建时间、回答正文和采纳状态。官方资料读取正文。Mozilla Bugzilla 通过公开 REST API 读取状态、时间和评论。网络请求保留 TLS 验证；部分直连失败的请求改用现有代理核查。

下列结果是定向便利样本，有站点、语言、存活页面与检索词偏差；多条讨论涉及同一工具，不能视为独立市场样本。历史记录只证明当时有人报告过问题，不证明最新版本仍有相同问题。搜索返回的无关页面和重复结果不计为证据。

## 四、真实缺陷线索：先验证适用范围

**B1 · [Mozilla Bug 2057680](https://bugzilla.mozilla.org/show_bug.cgi?id=2057680)：Container Settings dialog cropped after first use, hiding Cancel/Done buttons。**

- 创建于 2026-07-24；本轮读取状态为 `RESOLVED / FIXED`，目标里程碑为 `155 Branch`，最近变更时间为 2026-07-30。状态来自维护系统，不代表本项目已复验。
- 评论 #0：报告者在 macOS 15.7.5、Nightly 154 中首次打开容器设置正常，再次打开同类弹窗时看不到 Cancel / Done；手动调整面板大小可让按钮重新出现。报告者明确认为窗口大小似乎不是决定因素，关闭设置标签或窗口后也会再现。
- 评论 #1：另一条反馈称调整大小后，下一次打开仍可能过小而裁切按钮。评论 #2 给出回归区间；#4、#5 记录补丁和落地；#9 的维护者申请说明称修复是通过模块导入让弹窗同步渲染，并自报已覆盖自动化测试、在 Nightly 验证。
- 可追溯的修复入口：[D314267](https://phabricator.services.mozilla.com/D314267)、[autoland revision](https://hg.mozilla.org/integration/autoland/rev/bd86aeb7ccd9)。本轮只核查 Bugzilla 中的发布记录，**未审查补丁正文，未下载录像，未本地复现**。
- 对 Layress 的启示：准备步骤必须区分首次和再次打开；尺寸压力与状态或时序引起的裁切应分别归因。不能只保存一个窗口宽度就声称可回放。
- 适用范围限制：这是 macOS 上 Firefox 自身设置界面，不是已确认可由首版 Windows / Chromium Web 或 Electron 通道接入的页面。只作为真实历史缺陷线索，**不纳入首版评估集，不据此扩大平台承诺**；许可与样本再分发也尚未核查。

## 七、2026-11-05 续查：先理解日常基础需求

### 调研问题与结论

用户本轮要求：不要只调查别人尚未解决的问题，也要理解用户需要哪些基础功能。本轮因此改问“改完界面后，用户怎样完成一次检查”，而不是先问“还能增加什么独特检测规则”。

初步任务链是：**进入实际待测页面 → 选择目标尺寸和状态 → 查看页面与常用操作 → 留下能交接的证据 → 修复后重复检查**。用户需要这条链方便、稳定地完成；其中的能力即使已有工具提供，仍可能是产品可用的基础门槛。基础需求存在、值得在 Layress 中提供、需要独立自研，是三个不同判断。

本轮新增核查 10 条用户提问 / Issue 及相关回答或评论，另读 7 份官方能力资料；以下是定向便利样本，**不能声称代表大多数用户、需求频率或市场优先级统计**。没有访谈、试用、实跑或付费验证；本轮提出的优先核查顺序不是已批准实现清单。

### 按用户任务归纳的基础需求

这张表是本轮证据支持的待验证需求，最低完成标准为我们的归纳，尚未经目标用户验收；核查顺序不代表已经确定版本范围。

| 基础任务 | 值得优先核查的最低完成标准 | 依据与需要避免的偏差 |
|---|---|---|
| 1 · 快速开始一次检查 | 能到达实际待测页面，准备步骤与失败原因清楚，不为当前任务额外强制注册工具账号或配置不必要服务 | U8、U2；是否以 URL、本地启动入口或已有浏览器状态接入，仍需分别验证，不预设零配置接任意应用 |
| 2 · 省去重复切尺寸和收集画面 | 自选少量常用宽高，知道当前实际条件；重复查看相同页面和状态，必要时批量留图 | U5、U7 与 Emulation；不要求一开始穷举所有设备，也不能将“同时展示多个视图”直接认定为唯一方案 |
| 3 · 检查真正要用的页面与操作 | 登录后、菜单展开、弹窗与表单等目标状态能准备到位，既有测试或人工步骤能接续 | U3、U6、U9；登录有直接证据，菜单 / 表单状态的具体频率仍需补证，不能自动扩大为任意业务路径探索 |
| 4 · 结果能看懂、找到并交给同事 | 现场截图和尺寸 / 状态标签对应，输出目录可见，能定位问题所在页面或操作；人工待确认项清楚 | U4、U5、U7、U10；基础截图、上下文和交接很重要，不等于已验证用户需要复杂仪表盘、云账号或所有报告格式 |
| 5 · 下一轮还能低成本重查 | 准备配置可复用，变化后能重跑相同任务；环境和工具错误可排查，维护耗时不超过节省的检查时间 | U1、U2 与官方稳定性建议；不能从官方机制推算误报率，也不能把“有自动化”直接等同于节省时间 |
| 6 · 在已有流程里逐步采用 | 先完成一件检查任务，已有脚本、截图工具和报告能继续使用；需要时再考虑批处理 / CI / 结构化结果 | U2、U4、U6 与 Reporters；CI 的独立用户需求和频率本轮不足，Agent 结构化接口是既有产品约束，不冒充本轮新发现的普遍要求 |

基础检测仍可包含开发者关心的裁切、溢出或操作区被遮挡，但本轮不能从这些帖子得出“用户最想要某一规则”的排名；文字截断、滚动、折叠本身也不必然是缺陷。**基础可用性与差异化价值都要验证**：前者关心能否方便完成整次检查，后者再看压力搜索、确认与缩减是否带来额外收益。

### 下一轮怎样补证、怎样收口

- **先按任务比较已有办法**：围绕一个有登录或明确状态的页面、用户选定的少量尺寸，比较浏览器人工检查、多视口预览和已有自动化的准备、检查、交接、修复后重查成本；本轮只提出比较问题，没有启动实验或承诺具体工具可直接接入。
- **围绕近期真实任务访谈**：最近一次发布前检查了哪些页面和操作、选了哪些尺寸及原因；逐步做了什么、哪里重复；问题怎样交给同事、修复后怎样确认；已有工具哪里足够、何时回到人工；愿意额外准备多久、哪些数据不能上传。联系对象、发帖或索取试用均需另行授权。
- **区分用户群再排顺序**：个人开发者、已有 Playwright 的小团队、QA / 多语言团队的起点不同；中文 APP 反馈只作跨范围参考，缺少直接中文 Web / Electron 使用者和近期代表样本，不用旧帖替代当前需求确认。
- **不为差异化牺牲基础链路，也不照抄全套竞品**：已有机制能低成本满足时优先复用；基础接入、稳定性和证据交接未证明可用时，不以发现一个复杂历史缺陷宣称产品方向成立。

检索边界：中文围绕多语言截图审核、UI 自动化维护与响应式人工检查检索；英文围绕认证复用、失败截图 / 报告和保存路径检索，原文受限后通过 Stack Exchange API 补核。另在 Responsively 仓库以标题 `screenshot`、`login` 定向检索，按评论排序各取前 5 条，再读取上表相关 Issue 的评论；排序和截断会偏向历史热门问题，不是全量样本。官方 Chrome Device Mode 页面本轮抓取失败，未据此新增能力结论；较旧博客及未取得正文的新帖未计入上述 10 条证据。本轮未执行任何目标应用、竞品或人工验收，也未开发功能或对外联系。
