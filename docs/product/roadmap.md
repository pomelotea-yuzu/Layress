## 阶段与证据门槛

| 阶段 | 准备做什么 | 进入下一阶段前要有的证据 |
|---|---|---|
| 1 · 需求与社区调研（当前） | 先查日常界面检查任务、基础体验与现有工作流，再用真实缺陷、竞品和条件允许时的实跑核查差异化价值 | 明确首批用户、常见任务与最低完成标准；区分基础需要和自研必要性，关键判断有来源、反证与未决项，剩余关键疑问明确到需要实验才能回答 |
| 2 · 最小技术验证 | 依据调研修订首验提案，确定一种关键操作失效及对照，批准范围后开独立 change | 已知好坏样本判断符合人工真值；触发条件可重复回放；探针与存储路径约束有实测依据 |
| 3 · 外部项目验证 | 扩充真实正负例，与朴素规则和可运行竞品比较 | 在外部案例中证明检测或复核收益，记录误报、漏报、接入成本与不确定性，决定继续、收缩或做插件 |
| 4 · CLI 预览版 | 做成可独立接入的 CLI、可读报告与有版本的结构化结果 | 外部使用者能独立接入并重复使用；确认、缩减与回放的限制清楚，人工未复核项单列 |
| 5 · 扩展与发行 | 根据持续使用反馈决定发行及 Electron、CI、MCP / Skill 等能力的交付顺序 | 新能力有具体需求和维护依据，满足对应验收与发行条件；不预先承诺全部实现 |

## 当前接手从哪里开始

2026-11-05 收工停点、阅读顺序和下次最小交付见[综合调研第十节](../research/2026-11-05-user-needs-and-agent-augmentation-research.md)：先整理一个真实任务的准备与判据，不自动启动应用或进入开发。

1. 先读[基础需求与 AI Agent 增强调研汇总](../research/2026-11-05-user-needs-and-agent-augmentation-research.md)，从用户本人自有应用的近期开发与检查记录提取任务；具体标识和证据仅留本地草稿。优先整理语言切换后继续编辑与取消、窗口变化后阅读与操作等任务，再按需补外部用户和[社区原始证据](../research/2026-11-04-community-evidence-round-one.md)；历史困难不直接当成今天仍未解决的需求。
2. 将基础体验的最低完成标准与差异化收益分别核查：前者关心任务能否方便、稳定地完成，后者再看压力搜索、确认和缩减是否节省时间；结合[已有桌面调研](../research/2026-11-03-web-electron-ui-stress-test-tool-market-and-open-source-research.md)与[第二轮 GitHub 证据](../research/2026-11-04-github-evidence-round-two.md)，保留人工检查、免费工具和已有测试足够的反证。
3. 按用户任务比较自建、复用和集成的代价，再决定下一步最值得验证的问题；访谈与试用优先追问最近一次真实任务的步骤、耗时和完成标准，联系或发帖前另行取得授权。

[VS Code 候选准备与 2026-11-05 续查](../research/2026-11-04-vscode-candidate-readiness.md)保留为后续验证线索：原 profile 仍缺失，另有同修复的较小触发入口；尚未复现，不进入评估集，也不再默认作为下一步调研的唯一入口，候选选择不代表开发方向已定。

调研记录归 `docs/research/`，按日期命名；结论必须能追溯到证据。无需为了补齐资料而无限延长调研，也不以预设开发日期代替调研收口判断。
