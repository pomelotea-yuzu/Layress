# Layress · 简短路线图

> 当前规划依据：2026-11-04 用户讨论。先把调研做清楚，再决定验证与开发投入，不急于开工。
> 本文供后续对话与 Agent 接手；阶段顺序作为当前依据，后续范围随证据修订，不承诺发行日期。

## 阶段与证据门槛

| 阶段 | 准备做什么 | 进入下一阶段前要有的证据 |
|---|---|---|
| 1 · 需求与社区调研（当前） | 查真实缺陷、社区讨论、修复 PR；了解现有处理流程，核查竞品并在条件允许时实跑 | 明确首批用户和高频场景；关键判断有来源、反证与未决项，剩余关键疑问明确到需要实验才能回答 |
| 2 · 最小技术验证 | 依据调研修订首验提案，确定一种关键操作失效及对照，批准范围后开独立 change | 已知好坏样本判断符合人工真值；触发条件可重复回放；探针与存储路径约束有实测依据 |
| 3 · 外部项目验证 | 扩充真实正负例，与朴素规则和可运行竞品比较 | 在外部案例中证明检测或复核收益，记录误报、漏报、接入成本与不确定性，决定继续、收缩或做插件 |
| 4 · CLI 预览版 | 做成可独立接入的 CLI、可读报告与有版本的结构化结果 | 外部使用者能独立接入并重复使用；确认、缩减与回放的限制清楚，人工未复核项单列 |
| 5 · 扩展与发行 | 根据持续使用反馈决定发行及 Electron、CI、MCP / Skill 等能力的交付顺序 | 新能力有具体需求和维护依据，满足对应验收与发行条件；不预先承诺全部实现 |

## 当前接手从哪里开始

1. 读[已有桌面调研](../research/2026-11-03-web-electron-ui-stress-test-tool-market-and-open-source-research.md)、[首轮社区证据](../research/2026-11-04-community-evidence-round-one.md)与[第二轮 GitHub 证据及待续项](../research/2026-11-04-github-evidence-round-two.md)，区分公开能力声明、已核实事实与假设；尚未实跑的竞品、用户反馈缺口继续标明。
2. 补社区证据：真实项目的 Issue / 修复 PR、测试工具的误报与采用障碍、中文与英文开发者讨论；记录来源日期、触发条件、影响的关键操作、现有解法及剩余困难，不用热度代替需求。
3. 汇总哪些证据支持独立做、哪些支持复用或贡献现有项目，以及下一步最值得验证的问题；若需要访谈或试用，先准备问题与候选对象，联系或发帖前另行取得授权。

当前具体停点与下次第一步见[优先候选准备核查](../research/2026-11-04-vscode-candidate-readiness.md)：先补 VS Code V1 的触发 profile 与发布者数据，再决定隔离试跑；尚未复现，不进入评估集。

调研记录归 `docs/research/`，按日期命名；结论必须能追溯到证据。无需为了补齐资料而无限延长调研，也不以预设开发日期代替调研收口判断。

## 与现有提案及 change 的关系

- [首个验证方案](../engineering/plans/2026-11-03-first-validation-plan.md)继续保留为**提案，待调研后修订与批准**；其 S0–S4、样本量和 6 周 / 90 小时均不视为已批准任务。
- 修订时重点复核：先核查外部样本与竞品可运行性、首轮规模、以样本真值判断输入通道、按被测进程归因写盘证据。
- 路线图管阶段目标，change 管当前确定执行的单项工作；调研和路线图文档可直接维护，技术实验与行为实现按[开发流程](../development/workflow.md)独立立项，不一次建立全部后续 change。
- 各阶段都允许依据反证收缩、转为插件或停止独立实现；继续投入以实际收益为依据。

暂缓：审美评分、自动修复、任意应用全自动探索、全平台全浏览器矩阵、最小 HTML / CSS 自动抽取；桌面 UI 与远程视觉模型的投入时点另议。
