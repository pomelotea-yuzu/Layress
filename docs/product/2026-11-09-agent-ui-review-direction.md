## 用户已经明确的目标

- 作者目前大三，未来约一年准备就业作品集；希望积累一个自己用得上、有 GitHub 或开源社区影响力的作品。
- 真实起点是使用 Agent 测试 Web / Electron 时，仍有实际使用细节需要人指出。
- 优先查公开使用者的共性问题，个人案例可用，但不要求用户先提供案例才能推进。
- 可以复用、集成和改进成熟方案，先做可用切片，边使用边改；不要求先证明市场空白、独创算法或 Agent 必然失败。
- 旧文档中的想法仍可查阅与引用；重新讨论不等于禁止读历史。允许智能体开展必要调查和仓库修改。

这些是用户决定。下面的具体功能排序、形态和开发顺序是建议，不包装为用户已经逐项批准。

## 从旧材料中继续使用什么

[综合调研](../research/2026-11-05-user-needs-and-agent-augmentation-research.md)已经明确两条需要共同考虑的使用路径：
**人愿意主动打开应用；不同 Agent 能调用能力并实际消费结果**。这一要求比“再提供一个浏览器工具”更完整。

可继续参考的任务链是：进入真实页面 → 选择条件和状态 → 检查 → 整理问题与证据 → 修复后重查。
登录状态、弹窗和表单准备、结果路径、低成本重查都属于基础体验；已有解法可以直接复用。

旧的[自主任务对照](../research/2026-11-08-blind-probe-result.md)在一个自造遮罩页面上没有观察到 Agent 假绿。
这足以反对“Agent 必然绕过遮挡并假报成功”的说法；它没有覆盖其他任务、其他工具、视觉细节或检查遗漏。
新阶段保留这条反证，不把它扩大为整个界面检查方向无价值，也不恢复原有立项闸门。

## 本轮公开资料：重复出现的问题类型

本轮通过公开 GitHub API 读取问题正文及相关评论，并读取项目 README。检索截至 2026-11-09，
定向覆盖 Playwright MCP、Browser Use、agent-browser、Agentation；不是抽样调查，不能声称代表大多数用户或得出频率排名。

| 类型 | 来源与已读内容 | 对产品的启示与证据边界 |
|---|---|---|

| 工具层错误没有正确传给调用方 | Browser Use [#5252](https://github.com/browser-use/browser-use/issues/5252)，2026-07-18；报告 MCP 执行失败却返回 `isError:false` | 调用失败、检查发现问题、未检查必须分别呈现；这是特定工具版本的报告，不能泛化为所有 Agent 都误判 |

| 视觉上下文与结构化页面信息不能互相替代 | Playwright MCP [#1816](https://github.com/microsoft/playwright-mcp/issues/1816)，2026-11-01；用户的 WebGL 对象不在可访问性快照中，工具说明又令助手停止看图操作 | 检查方法与不支持范围需要可见；[上游自动化评论](https://github.com/microsoft/playwright-mcp/issues/1816#issuecomment-6581850397)报告了修正，当前 README 已说明 vision 例外。不是本仓复现，也不据此把 Canvas/WebGL 纳入第一版 |
| 控件外观之外还有键盘和可访问性细节 | Agentation [#211](https://github.com/benjitaylor/agentation/issues/211)，2026-09-15；图标按钮命名、嵌套交互与焦点问题 | 适合复用 axe 等成熟检查。维护者[说明 3.1.0 已补命名、键盘激活和焦点返回](https://github.com/benjitaylor/agentation/issues/211#issuecomment-5756720261)，本轮未复测，不当作当前未修缺陷 |
| 人指出问题后，Agent 还需要可靠的定位上下文 | [Agentation README](https://github.com/benjitaylor/agentation)提供元素选择、批注、结构化反馈及 MCP；[#225](https://github.com/benjitaylor/agentation/issues/225)，2026-11-02，报告 React 19 下组件信息有时缺失 | 人工反馈交接已有成形方案，应参考其体验；组件源码定位有框架与版本边界，不能承诺任意页面映射到源码。README 能证明功能声明，Issue 能证明有人报告困难，均不等于本仓实测效果 |

这些来源支持优先处理“检查了什么、观察到什么、怎样交接和重查”的工作问题。
它们没有证明任何一个具体产品形态已经有市场，也没有证明只要汇总截图就足以减少人工细节检查。

浏览器工具的基础故障、模型判断失误、被测页面缺陷是三种不同原因，不能合并统计为 Layress 能发现的 UI Bug。
本轮 HN 检索包含推广、弱相关与较旧记录，没有拿它们补齐“多数人的需求”结论。

## 现成产品怎样分工

| 现成能力 | 当前资料说明什么 | Layress 的建议分工 |
|---|---|---|
| [Playwright](https://playwright.dev/) / [Playwright MCP](https://github.com/microsoft/playwright-mcp) | 浏览器操作、截图、状态和测试基础已成熟；当前 MCP README 还列出批注、录制、trace、测试断言，并比较 CLI + Skills 与 MCP 的适用场景 | 当底层基础设施复用，同时把“Agent 直接使用 Playwright”视为现成替代方案；不把 MCP、截图或批注当成独有能力 |
| [agent-browser](https://github.com/vercel-labs/agent-browser) | 当前 README 已列出 shell 调用、截图、diff、a11y、Electron skill、MCP、dashboard 等入口 | 不自行重造通用浏览器 Agent；后续选一种执行通道先接通，避免第一版同时维护多个适配层 |
| [Agentation](https://github.com/benjitaylor/agentation) | 人在界面上指出问题，再把定位信息交给 Agent；当前 README 要求 React 18+ 和桌面浏览器 | 学习人工复核与反馈体验。当前许可为 PolyForm Shield 1.0.0，不按 MIT / Apache 依赖直接复制竞争产品代码；本轮未复制任何上游代码 |
| 旧调研中的 breakhound / ui-review / LocalePass | 已有压力场景、几何候选和本地化等接近能力，详见[历史源码核查](../research/2026-11-04-github-evidence-round-two.md) | 可作场景和实现参考；本轮没有重跑或重新审计这些项目，不能把旧快照当成当前能力上限 |

“已有工具能做”不再是停止开发的理由；我们需要通过实际体验减少准备、翻找、复核和重查的负担。
上述是工程与产品建议，尚没有本仓实测的节省时间、准确率或用户留存数据。

## 建议定位与首个切片

建议先把 Layress 做成：**面向 AI 辅助开发的界面检查工作台，帮助人和 Agent 系统检查界面、复核具体问题，并在修复后重复检查。**

一次有用的体验是：输入开发中的页面 → 按少量明确条件执行检查 → 查看现场和候选问题 → 把定位信息交给 Agent → 在相同条件下重查。
“哪些条件和状态尚未检查”需要和问题一起展示；不以一次运行无告警宣称整站已经通过验收。

首个切片建议限制为一个无需真实账号的 Web 页面、用户可选的桌面与窄窗尺寸：

1. 复用 Playwright 采集截图、实际视口与页面状态；不要求先注册工具账号或配置模型 API key。
2. 接一小组成熟自动检查：axe 可访问性结果、页面横向溢出、明显文字裁切候选。裁切候选须允许标记为设计如此，例如合理省略号；不因出现滚动就报缺陷。
3. 提供可直接打开的本地可视报告，显示问题位置、条件和检查范围，允许人补充说明或忽略理由；视觉意见单列来源。
4. 同一份结果提供紧凑 JSON 与 Markdown，便于已有 Agent 定位、修改；先用 CLI / 文件接入验证，再按实际宿主需求增加 MCP / Skill。
5. 保存本次配置，修复后以相同条件重新检查。重查是新执行；只看旧截图属于证据查看，不能算重新验证。

报告与 CLI 共享事实，不要求先开发 Electron 外壳；Web 接入先做通，Electron 接入后续以真实应用验证，不写成已支持。
第一版不承诺自动理解全部业务结果、通用自主探索、自动源码定位、审美打分或全平台覆盖。
窗口 / 内容 / 语言压力检查仍可增量加入，无需开工时同时完成“扫描、确认、缩减、回放”四个独立包。

可演示的完成标准是：一个已知异常页面能显示具体现场，一个合理省略或滚动页面不会被直接定为缺陷；
人和 Agent 能读同一组问题，修改页面后能按同样条件重查。这个标准指导最小实现，不是本轮已经通过的验收。

## 开源与作品集怎么积累

先做能解释清楚的真实成果：可运行示例、带问题与修复的演示、准确的限制说明、可让外部贡献者加入的检查规则和案例。
星数与曝光是希望争取的结果；阶段进度可以用可独立使用、有人反馈、重复使用和贡献记录来观察。
每次迭代由实际使用暴露的问题驱动，不把长期访谈、完整竞品对照或商业化证明设为开工前置条件。
