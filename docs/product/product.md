## 产品与形态

**Layress 是面向个人开发者和小团队的本地界面验收助手。** 帮助使用 Agent 开发的人检查界面、指出问题、交给 Agent 修改，并重复检查相关任务。

11-09 确认的首版形态为本地服务 + Web 工作台，共用任务执行核心，Agent 先通过 CLI 调用。
11-10 根据用户对额外窗口、调整尺寸和截图搬运的反馈，当前优先评估 **Electron 单应用，在一个主窗口内操作被测页面、配置设备并原地反馈**。
具体承载方式尚未定稿，包体积与实际操作体验需要验证；共用任务事实与 Agent 非交互调用要求继续保留。MCP 在具体客户端需要时增加。
工具面向 Web / Electron 开发中的界面检查需求，具体被测技术与接入范围按已验证能力公布，不承诺任意应用开箱可用。

用户希望未来约一年积累就业作品集与开源影响力；可复用和集成成熟方案，边做边用、边改进。
不再以证明市场空白、Agent 必败或完成全部商业论证作为开工条件。

## 对人和 Agent 都简单

人的最短路径：**看到现场 → 圈出位置 → 写一句想法 → 交给 Agent → 看修改后的结果**。

例如：框住资料页底部的按钮，写“这里被底栏挡住了，缩小窗口后也要能保存”。
用户无需填写选择器、JSON、源码路径或正式测试用例。连接项目与 Agent 的准备尽量一次完成；普通反馈不重复配置这些信息。
清单、自动检查与执行记录可以帮助完整验收，但用户可以直接从圈画问题开始，不强制先编排一套测试计划。

Agent 应能通过简短命令发现能力、取得待处理任务和相关证据、提交处理结果、发起范围明确的复查。
使用有版本的结构化结果、稳定任务标识与明确错误，不要求解析整段运行日志或操作工作台按钮。
具体命令名、数据字段与兼容客户端在实现 change 中确定，不把这里的交互目标当成已交付接口。

## 圈画反馈怎样变得可执行

以下为实现建议，服务于已确认的易用性要求，不是本轮实测能力：

| 用户做什么 | 工具应自动整理什么 | Agent 应知道什么 |
|---|---|---|
| 点选元素、框选区域或简单画线 | 保留原始画面、标记区域和用户描述；界面只需少量直观标记方式 | 这条意见指向哪个位置、涉及哪些内容 |
| 写“这里太挤”“取消后别丢内容”等短句 | 保留原话，附当前页面、视口、时间和可取得的状态 | 用户希望发生什么；哪些解释还只是推测 |
| 点击交给 Agent | 建立稳定任务标识，关联现场与必要上下文；已连接时进入可读取任务列表 | 取得该任务的描述、标记图 / 局部图与证据入口 |
| Agent 处理问题 | 关联修改说明、新一轮检查和修改后画面 | 当前做到哪里，哪些检查失败、未执行或仍需判断 |
| 用户查看结果 | 展示原问题、原始现场与修改后现场；允许继续补充或重新打开 | 后续讨论属于同一个问题，不必重新猜测上下文 |

画面坐标需要绑定原始截图尺寸、当时视口与滚动状态，展示缩放不能让标记移位。
能取得 DOM 元素、文本或定位信息时自动附上；找不到可靠元素或源码时明确缺失，仍保留可用的区域反馈，不能猜造源码路径。
页面更新后，原现场与新现场分开保留；旧位置关联失效时重新定位，不能默认为仍指向同一个元素。

用户意见、实际观测与 Agent 建议分别保留来源。“这里不好看”等主观意见可以形成修改任务，不自动包装成检测确认的缺陷。
若描述影响实现且确实不明确，Agent 再提必要问题；不把每条短反馈都强制扩写成需求表单。

## 交给现有 Agent 的方式

工作台与 CLI 读写同一份任务与结果，避免两套记录分叉。已接入的 Agent 能读取待处理任务，后续接入形式不改变任务事实。
未连接 Agent 时，可提供复制反馈的退路，将描述、现场引用与任务标识交给用户当前使用的 Agent。
不能因为用户打开了工作台，就默认已经能向任意正在运行的聊天会话推送消息；具体连接方式必须验证并在界面上说明连接状态。

Layress 本地运行不等于调用它的 Agent 也本地运行。页面资料交给远程 Agent 时需说明数据去向；使用用户已有 Agent，不默认新增付费模型调用。
反馈描述与证据先在本地保存，是否交出以及交给哪个已连接入口由用户操作或已有显式授权决定。

## 验收与反馈如何连起来

人可以圈画创建问题，自动检查也可以提供候选问题；两者都能关联同一功能的验收任务与后续复查。
使用者不必在“反馈工具”和“测试工具”之间搬运同一条问题。

建议的人类可读状态为“待处理 → 处理中 → 待复核 → 已完成”，并允许标记阻塞或重新打开。
Agent 声称修好只代表提交处理结果，不能直接替用户完成主观意见的确认；有明确判据的自动复查按实际结果记录，未执行不得显示通过。
这些状态和呈现方式是建议，具体状态机在技术实现中定稿。

## 接入与首个可用体验

首个可用体验优先跑通：一个普通页面的现场捕获 → 圈画和一句话说明 → Agent 读取 → 修改结果回传 → 原问题复查。
一个页面只是开发验证样例，不将“只服务弹窗”或“只查窄窗”作为产品定位。
随后把可复用的验收任务、自动检查和历史结果接上，保持用户可直接从一个问题开始。

**设备选择与配置恢复是基础流程的一部分**（2026-11-10 用户补充）：被测网页可能在电脑、手机等设备上使用，
进入页面检查前应可选择设备，并保留上次选择，减少重复设置。
设备预设、视口、横竖屏和配置归属的具体交互在[第一阶段讨论稿](2026-11-10-stage-one-experience-and-access.md)中细化；
浏览器设备模拟与真实设备运行必须分别标明，不能把缩小窗口或模拟手机当成手机真机验证。

Web 工作台需要一种可靠取得被测现场的方式。截图 / 采集画面的圈画、受控浏览器会话、页面内批注等方案需实际验证；
不能假设任意 URL 放进 iframe 后就能读取 DOM 或注入绘图层。第一轮可以从已采集现场上的圈画开始，不据此承诺任意网站实时编辑。
选中元素后的源码定位可以逐步增加，不能把用户必须安装某个框架插件作为所有反馈的通用前提。

复用成熟浏览器操作、批注和检测能力，按实际许可选择依赖；本轮调研已发现相近产品，不宣传圈画或 MCP 是独有能力。
价值需要通过完整流程体现：人是否少描述、Agent 是否少猜位置、修复后是否容易检查原问题。
